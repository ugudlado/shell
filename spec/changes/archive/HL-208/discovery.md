# Discovery Brief — Verify Command Portability

**Feature**: Wire schema verify.commands to read from project.yaml instead of hardcoding type-check/test/build.

---

## What I Understand

Schemas (feature, bugfix, chore) hardcode `type-check`, `test`, `build` as verify commands. This fails in repos without those exact script names. project.yaml (now generated by bootstrap per HL-207) has the correct stack-adapted verify commands. Schemas should reference project.yaml instead.

---

## What Already Exists

- `feature.yaml`: hardcoded `[type-check, test, build]` in implement and complete phases
- `bugfix.yaml`: same
- `chore.yaml`: same  
- `spike.yaml`: no verify commands (correct for exploration)
- `project.yaml`: has `context.tech_stack` and the verify info is implied by the stack but not yet an explicit field

---

## Key Decisions

### D1: Add explicit `verify_commands` field to project.yaml

The generate-project-yaml step (HL-207) already maps stacks to verify commands. Add an explicit `verify_commands` list to project.yaml so schemas can reference it:
```yaml
verify_commands:
  - type-check
  - test
  - lint
```

### D2: Schema verify.commands uses variable reference

Replace hardcoded lists with: `$project.verify_commands` — the orchestrator resolves this from project.yaml at runtime.

---

## Scope

### In-Scope
- Add `verify_commands` field to project.yaml format (update generate-project-yaml step)
- Update feature.yaml, bugfix.yaml, chore.yaml to use `$project.verify_commands`
- Update this repo's project.yaml to include `verify_commands`

### Out-of-Scope
- spike.yaml (no verify commands)
- bootstrap.yaml (no verify commands)
